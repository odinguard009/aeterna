# Aeterna session runner

The repo CLAUDE.md is the source of truth; this skill only orders its steps. Do not re-read CLAUDE.md (it loads automatically).

## Start (one call each, condensed output)
0. Auto mode ("idle chain", rules: `docs/ai/next-session-prompt.md`). Scheduled runs: right after `add_repo` and BEFORE the clone run `gh api repos/odinguard009/aeterna/contents/tools/session_gate.sh --jq .content | base64 -d | bash -s check` (from their prompt); anything but GO = end the run at once. Manual sessions skip `check`. The owner commands `otomatis on|off|status` run the same one-liner with `on`, `off` or `status` (no clone) and end there.
1. `add_repo` odinguard009/aeterna (push access), then ONE light sparse clone exactly as CLAUDE.md says (generous timeout, never two git operations at once), then `register_repo_root`.
2. If `docs/ai/chain-stop.md` exists: stop at once unless the owner is present and has answered (then delete the file and continue).
3. `bash tools/session_start.sh`. Exit 3 / `OVERLAP` (an active `LOCK`/`MANUAL` on issue #1; fallback when gh fails: a `v*` release commit under 30 minutes old) = another session is running: stop and tell the owner. Then mark the session: scheduled runs `bash tools/session_gate.sh lock`, manual sessions `bash tools/session_gate.sh manual` (exit 3 = an auto session holds the lock: stop and tell the owner). A crashed session's mark expires (LOCK 5 h, MANUAL 3 h).
4. Context in one call: `git log --oneline -5`, open issue titles (`gh api "repos/odinguard009/aeterna/issues?state=open" --jq '.[] | "#\(.number) \(.title)"'`), newest handoff comment of the roadmap issue.
5. Schedules are not touched by sessions (one recurring task, installed by the owner; `docs/ai/next-session-prompt.md`). Never call `create_trigger`, `update_trigger` or `delete_trigger`.
6. Read `docs/ai/roadmap-open.md`, size the session (small bundle of 3-5, or one heavy task alone) and open with ONE Indonesian line: `Ver. X.Y.Z (rencana) - gunakan model Opus - <scope> - Token awal: <the total_tokens value shown at the start of the session>` (pick the work from `docs/reports/unlock-report.md` when the plan in `roadmap-open.md` leaves a choice) (owner, 2026-10-17: Opus for every session and subagent). If the running model differs, say so once and continue (the main model cannot be switched mid-session). 
7. **Lane session** (owner says "Lanjutkan roadmap ui" or "... card"; P1, `docs/ai/lanes/README.md`): step 3 becomes `bash tools/session_start.sh --lane <lane>` and `bash tools/session_gate.sh manual <lane>` (scheduled: `lock <lane>`); the opening line says `lane <lane>`. During: own files only, no version bump / CHANGELOG / roadmap edits (notes in `docs/ai/lanes/<lane>.md` instead; `node tools/lanes.mjs --unstage-shared` before a commit). End: push `lane/<lane>`, `bash tools/session_gate.sh lanedone <lane> lane/<lane>`; if the other lane already shows `LANEDONE` (or has nothing new) in `session_gate.sh status`, continue with the merge step: back on `main`, `bash tools/lane_merge.sh`, apply the notes, one version bump, then End steps 1-6 as usual. Otherwise send no game file (nothing is released yet), short Indonesian summary with tokens, stop.
8. Every 3rd session or before a minor release: player-view pass (skill `bs-playwright-tester`), run as a parallel subagent at the start; failures are fixed before new features.

## During
- Previous Regression (printed by `session_start.sh`): `failure` = fix it first; `in_progress` = check again before your push.
- Per task: test/scenario first for a new mechanic, `npm run -s loop`, one local commit (the first one also bumps the version and opens the CHANGELOG heading; one version per session). Push once at the end; `git fetch origin main` + rebase before every push.
- Parallel subagents (CLAUDE.md): start the `bs-playwright-tester` pass and data lookups as subagents while the main session writes code; they report, the main session fixes and commits. Scheduled runs: before starting the next task run `bash tools/session_gate.sh switch`; OFF = no new task, go to End.
- **Card-session prep in parallel (owner, 2026-10-18 21:56):** in every card session, at the start, launch two read-only subagents while the main session works on the current head: (a) size the NEXT one or two heads in the roadmap order with `python3 tools/lever_report.py` + a scratch recompile (scratch output under `build/` or the scratchpad only, never `data/` or the engine) and report real unlocks; (b) collect the rules text and card data the next head needs (Fandom wiki API, official rules/card list; e.g. Super Unleash, Invoke, Succession rules, missing Brave combine data). The main session writes both results to `docs/ai/roadmap-open.md` (or the report the convention names) in its last commit, so the next card session starts from measured numbers and gathered sources. Which heads: the roadmap order first; then, so no kind of card is missed (owner, 2026-10-18 22:38), the highest "Waiting" rows of `docs/reports/mechanic-inventory.md` whose Prep is not `RDL` yet (item K in `roadmap-open.md`). Subagent (b) also verifies the status of up to 10 "(unverified)" rows per session (grep the engine and the glossary, never guess). The main session writes the results into `data/glossary/mechanics.json` (`prep.rules`, `prep.data`, `prep.lever`, `status`, `verified: true`, `note`). Optional third: a data/image check of one colour deck (`bs-card-data-check`). Skip when the session is low on calls; never let them edit code.
- A task that fails twice is dropped, named in the release notes and recorded in `docs/ai/roadmap-open.md` as `blocked (reason, date)`, so the next run takes another item and never repeats it blindly. If every open item is blocked, commit `docs/ai/chain-stop.md`.
- Past ~80 calls: push, handoff comment (done / next / failing seed / tokens used so far), stop and `bash tools/session_gate.sh unlock` (manual and scheduled); the next run continues.
- Usage / quota / rate-limit error: do not retry and do not touch schedules; push what is committed, handoff comment, `bash tools/session_gate.sh unlock`, stop.

## End (in this order)
1. Release gate per `docs/ai/release.md`: push, wait for **CI** only (needed for the GitHub Release), dispatch Regression (`sims=10` patch, `30` minor) and do **not** wait for it; the next session reads its result (a `fuzz` failure there: download artifact `fuzz-cases`, commit the case, fix it first).
2. `python3 tools/unlock_report.py` (refreshes `docs/reports/unlock-report.md`) and `python3 tools/mechanic_inventory.py` (refreshes `docs/reports/mechanic-inventory.md`; a mechanic finished this session gets `status: done`, `verified: true` in `data/glossary/mechanics.json` first). Update `docs/roadmap-data.json` (statuses, `updated`, `next`), the `**Done:**` / `**Next:**` lines of the CLAUDE.md Roadmap (`session_start.sh` prints the Next line, so a stale one misleads the next session) and delete finished items in `docs/ai/roadmap-open.md`; `node tools/gen_roadmap.mjs`, final commit + push.
3. Backup (owner: every 5 releases, not every session, not every commit): newest backup `B=$(git ls-remote --heads origin 'backup/*' | sed 's#.*refs/heads/##' | sort -V | tail -1)`; releases since then `gh api repos/odinguard009/aeterna/compare/$B...main --jq '[.commits[].commit.message | select(test("^v[0-9]"))] | length'` (chore/docs commits do not count). Due when it is >= 5: `git push origin HEAD:refs/heads/backup/vX.Y.Z`. A UI change keeps its own backup of the previous state (CLAUDE.md). Not due: run step 4 with `--no-backup`. Branch housekeeping: keep the newest 3 `backup/v*` branches; older ones whose tip is on `main` are listed with name + SHA in `docs/ai/deleted-branches.md` (restorable with `git push origin <sha>:refs/heads/<name>`); the session proxy blocks branch deletion, so the owner deletes them on GitHub.
4. Deliver the game: copy `index.html` to `/mnt/user-data/outputs/aeterna-vX.Y.Z.html`, then `node tools/session_end_check.mjs` (game file + embedded version, `test:release` on it, mind map fresh, `backup/vX.Y.Z` on origin; `--no-backup` only when no backup is due). It must pass. Check that the Release workflow made the GitHub Release (it runs after CI on `main`; one call: `gh api repos/odinguard009/aeterna/releases/tags/vX.Y.Z --jq '.assets[].name'` lists `aeterna-vX.Y.Z.html`; a docs-only last commit starts no CI, so the release of a version comes from the CI run of its version commit). Not there after CI finished: read the Release run's failing lines and note it in the final message. Then SendUserFile that HTML **and** `docs/roadmap.html` to the owner (owner, 2026-10-16: the playable file must always be sent, not only the mind map). Do not close the session before both files are sent.
5. No scheduling: sessions never create schedules; the next session is either the owner's "Lanjutkan roadmap" or the auto run 30+ minutes later (when the switch is ON). Commit `docs/ai/chain-stop.md` only when the roadmap is empty or every item is blocked.
6. Every session, after both files are sent: `bash tools/session_gate.sh done vX.Y.Z next=Opus` (always Opus since 2026-10-17; this starts the 20-minute idle timer; `unlock` instead on an early stop or error). Name the session "Ver. X.Y.Z" (if no rename tool exists, start the final message with `Ver. X.Y.Z`). Short Indonesian summary that shows `Playable: X / 8,041` (from `tools/unlock_report.py --line`), `Token terpakai: <Token awal minus the total_tokens value left now>` (read the counter after the last tool call; it is the budget-counter difference, effective tokens incl. cache re-reads, so it can differ from the billed figure; the owner can run skill `explain-usage` for a breakdown) and the line `Mode otomatis: ON|OFF` (from `bash tools/session_gate.sh switch`), and ends with the next session's model hint `gunakan model Opus` (read the next item in `roadmap-open.md`: heavy = Opus, small bundle = Sonnet); after the release, stop (questions go to a new session).
