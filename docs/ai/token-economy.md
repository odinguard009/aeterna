# Token economy plan (user decision 2026-10-14: "no compromise on quality, but save tokens")

Goal: the same quality per release with far fewer tokens. Each rule says who does it.

## 1. Session start (Claude)
- CLAUDE.md is loaded automatically: do not re-read it, the README, CHANGELOG or big docs "for context".
- Backlog in one short command, titles only:
  `gh api "repos/odinguard009/aeterna/issues?state=open" --jq '.[] | "#\(.number) \(.title)"'`
- Open only the issue you work on (`gh api repos/odinguard009/aeterna/issues/N --jq .body`).

## 2. Reading code (Claude)
- Look the name up in `docs/ai/code-map.md` (~1.2k tokens, regenerated by every build), then `grep -n` in that part, then `Read` with `offset`/`limit` for just that function. Never read `index.html`, `build/`, `data/cards/all-cards.json` or the card pack whole.
- Card data: query with a one-line `python3 -c` (only the fields needed), never print whole JSON.

## 3. Running things (Claude)
- Every command prints only what decides the next step: pipe through `grep -E "^not ok|^# (pass|fail)"`, `tail -3`, `--jq`. No raw logs, no full test listings.
- Work loop: `npm run -s loop` = build -> lint -> quick tests in ONE tool call with a one-line result (failures print only the failing lines). `test:quick` runs every `tests/unit/*.test.mjs` except the slow ones in `tools/quick-tests.mjs`, so new test files need no `package.json` edit. Python suites only for UI flows the change touches.
- No local full regression and no local sims: GitHub runs them (dispatch, see `release.md`; 10 sims for a patch, 30 for a minor). Regression is not awaited (owner, 2026-10-18); the next session reads it. To wait for **CI** on your push use ONE command:
  `for i in $(seq 1 40); do s=$(gh api "repos/odinguard009/aeterna/actions/runs?per_page=6" --jq '[.workflow_runs[] | select(.head_sha=="'$(git rev-parse HEAD)'")] | map("\(.name):\(.status):\(.conclusion)") | join(" ")'); case "$s" in *in_progress*|*queued*|"") sleep 30;; *) echo "$s"; break;; esac; done`
  On failure read only the failing lines: `gh run view <id> --log-failed | grep -E "BAD|FAIL|Error" | head -20` (or the `last-run-*` artifact).
- Screenshots only when the UI changed, one per layout.
- A failing seed is debugged by replaying that one seed, never by rerunning many games.

## 4. Writing (Claude)
- Chat replies to the user: a few sentences, no step recaps (the task list shows progress).
- Release notes and docs: bullet points, only what changed.
- Project docs: write only the files that changed; no copies of repo data (card JSON lives in the repo only).
- Do not re-propose skills or rewrite docs that did not change.

## 5. Scope (user + Claude)
- Scope per session is decided by Claude (see CLAUDE.md "Session scope"): small tasks bundled, a heavy task alone; start each session with one complete instruction, e.g. "Kerjakan issue #1" (CLAUDE.md is loaded automatically; saying "Baca CLAUDE.md" only triggers a wasted read). Extra instructions mid-task and "stop" cause rework: send them before starting when possible.
- Model choice (owner, 2026-10-17): Opus for every session and subagent (replaces the earlier Sonnet/Opus split); save tokens through scope and tooling, not the model.
- Brainstorming chat: upload `build/aeterna-docs-pack.md` (`node tools/pack_ai.mjs --docs`, ~17k tokens), not the full code pack (~86k).

## 6. Settings (user)
- Turn off the plugins and skills this project does not use (e.g. AnimatedWebs, Revenue Grid, Data, Design, Productivity): their descriptions are loaded into every message.
- Keep the Project docs small (done in v0.30.1: card JSON copies removed, a short card list kept).
- Ask "explain usage" at the end of a session to see where the tokens went, and tell Claude what to cut next.

## 7. Ideas taken from the Aegis repo (v0.30.1)
- Progressive disclosure: CLAUDE.md holds only the rules needed on every task and routes to topic docs (`docs/ai/cards-and-rules.md`, `docs/ai/release.md`) with a reading condition; workflows live in skills, not repeated in CLAUDE.md.
- A generated code map so the code is never explored blindly.
- A pre-push hook (`.githooks/pre-push`: build check, lint, quick tests) so CI/Regression minutes and polling are not spent on broken pushes.
- Replay-first bug reproduction (already in place: seeds and `BS.runReplay`).

## 9. Lessons from v0.31 (2026-10-14, ~300k tokens, 33 min)
- Biggest waste: a second full Regression run because two Python checks still used a removed function and an old label. Fix: `tools/check_renames.py` in the pre-push hook (seconds, no browser): removed top-level names still used in tests, removed labels still asserted, case-sensitive label checks that are not Title Case. Verified: it reports exactly the three misses of v0.31.
- Project docs trimmed to `CLAUDE.md` + `card-list.md` (they are loaded into every message; all other docs live in the repo and are read only when needed). Do not copy repo docs back into the Project.
- Every tool call re-sends the whole context: batch commands, prefer one script over several small calls.
- Repo not attached at session start cost three failed clones: call `add_repo` first.

## 12. Budget after v0.39 (estimate 2026-10-14, effective tokens incl. cache re-reads)
v0.35-v0.39 were built before this plan was written. Basis: a minor release ~2M in ~60-70 calls; ~16k fixed context per call; history grows with every call and image.
| Next work | Without the rules below | Target |
|---|---|---|
| v0.40 yellow (last colour) | 2-3M | 1.0-1.5M |
| Magic effect types (blue, green, purple Magic in one version) | 2-3M | 1.2-1.8M |
| Image check of the four colour decks (contact sheets) | 3-5M | 0.8-1.2M |
| UI patch (approved items together) | 1-1.5M | 0.5-0.8M |
Rules to hit the target:
- Colour versions follow `docs/ai/colour-version.md`; legacy suites read counts from the card data (v0.39.1), so no extra patch + Regression run per deck (v0.37.1 was one).
- Shared mechanics once: Magic effect types are needed by three decks, so build them in one version instead of piecemeal.
- Images: contact sheets of ~20 cropped corners, one colour at a time, only fields that are unverified (`note` on the card); every image stays in the history and is re-sent on every later call.
- Calls <= 60 per version; one script per step; `npm run -s loop`.
- Past ~80 calls: push, leave a handoff comment on the issue (done / next / failing seed), continue in a new session.
- Model (the owner picks it at session start): Opus for engine work (Magic types); Sonnet for yellow, the image check and the UI patch.
- After the release: stop; questions go to a separate session.

## 16. Auto mode / idle chain (2026-10-16)
- Idle runs end at the gate `check` (one `gh api` script, no clone), so a STOP run costs a few thousand tokens; the switch and session state are issue #1 comments, read with `since=7 days`.
- Between tasks an auto session spends one `switch` call; nothing else is added to a session.
- Each fired run still opens a session in the owner's list; for a long pause the owner can disable the task in the app instead of `OFF`.
